A **finite state machine (FSM)** is a way of describing behaviour in which a robot is always in exactly one of a fixed list of **states**, such as charging, cleaning or returning to its dock, and moves to a different state only when a specific event triggers a **transition**. It is one of the most basic models of computation, fully defined by its states, its starting state and the inputs that trigger each transition ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)). In robotics it is the usual first way to organise what a robot is doing, and it also runs inside ROS 2 itself: every managed node moves through a small, fixed set of states ([ROS 2 design: managed nodes](https://design.ros2.org/articles/node_lifecycle.html)).

This page explains how an FSM works, walks through a robot vacuum example with a state table and Python code, then covers hierarchical state machines, how FSMs compare with [behaviour trees](/atlas/concept/behavior-trees), and the ROS tools that implement them.

## Start here: a robot that can only be doing one thing

Imagine a row of cards on a table, one for each thing a robot vacuum can be doing: CHARGING, CLEANING, AVOIDING, RETURNING, STUCK. Exactly one card is face up. On the back of each card is a short list of rules: "if the bumper hits, flip to AVOIDING"; "if the battery drops below 15%, flip to RETURNING". Nothing else is allowed to change which card is up.

That is a finite state machine. "Finite" because the list of cards is fixed in advance. "State" because each card describes a situation the robot is in while it waits for something to happen.

It matters for robots because the same input means different things in different situations. A bumper hit while cleaning means "back off and turn"; a bumper hit while driving onto the dock may simply mean "arrived". In an FSM, what the robot does with an event depends on the state it is in. Vending machines, lifts, traffic lights and combination locks work the same way ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)).

## How it works

### States, events, guards and actions

An FSM in a robot is built from five pieces:

- **States.** The situations the robot can be in. Exactly one is active at a time.
- **Initial state.** Where the machine starts. On a diagram it is marked by an arrow from a black dot.
- **Events (or inputs).** Things that happen: a sensor crossing a threshold, a timer running out, a button press, an action finishing.
- **Guards.** A true-or-false condition checked when an event arrives. If it is false, the transition does not fire. In the diagram above, "start" only leaves CHARGING if the battery is at least 80%.
- **Actions.** Work done along the way. An **entry action** runs whenever a state is entered and an **exit action** whenever it is left, no matter which arrow was taken; a **transition action** runs only on one particular arrow ([Boost.MSM UML guide](https://www.boost.org/latest/doc/antora/msm/uml-short-guide.html), [Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)).

A transition is fully described by five things: source state, event, guard, target state and action. Write one row per transition and you have a **state-transition table**, which is the whole design in a form you can check line by line. In the designs on this page, an event that has no row for the current state is simply ignored, much as a turnstile that is already unlocked ignores another coin.

### Moore and Mealy machines

There are two classic ways for an FSM to produce output ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)):

- In a **Moore machine**, the output depends only on the current state. In practice that means the work lives in entry actions: entering OPENING starts a door motor, entering OPENED stops it.
- In a **Mealy machine**, the output depends on the state *and* the input, so the work lives on the transitions: "if `close` arrives while open, start the motor". Mealy designs often need fewer states, because the in-between states can disappear.

Real robot code usually mixes the two, and UML state machines support both: entry and exit actions belong to states, as in Moore, while transition actions depend on the triggering event, as in Mealy ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)).

Robot task logic is normally **deterministic**: every state-and-event pair leads to exactly one next state, so you always know what the robot will do next. (Theory also has non-deterministic FSMs, but any of them can be converted into an equivalent deterministic one; [Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine).)

## Worked example: a robot vacuum

Here is the machine from the diagram as a state table. It is a simplified teaching design, not any manufacturer's firmware.

| State | Event [guard] | Next state | Action |
|---|---|---|---|
| CHARGING | start [battery ≥ 80%] | CLEANING | entry: brush on, drive forward |
| CLEANING | bumper hit | AVOIDING | exit: brush off; entry: reverse a little, turn |
| AVOIDING | turn done | CLEANING | entry: brush on, drive forward |
| CLEANING | battery < 15% | RETURNING | exit: brush off; entry: follow dock beacon |
| AVOIDING | battery < 15% | RETURNING | entry: follow dock beacon |
| RETURNING | dock reached | CHARGING | entry: stop, start charging |
| CLEANING, AVOIDING, RETURNING | wheels stalled for 3 s | STUCK | entry: stop, beep (from CLEANING, exit: brush off first) |
| STUCK | button pressed | CLEANING | entry: brush on, drive forward |

Three things are worth noticing.

1. **The table finds gaps for you.** What should a bumper hit do while RETURNING? There is no row, so the robot ignores it and keeps pushing against whatever it hit. Writing the table is how you discover that question at a desk instead of in someone's living room.
2. **Some events have to be repeated.** "Battery low" needs its own row from CLEANING and from AVOIDING; "wheels stalled" needs one from three states. Every condition that can interrupt several states multiplies rows. That is the start of the state-explosion problem, covered below.
3. **Entry actions keep it tidy.** Because CLEANING's entry action turns the brush on, it does not matter whether the robot arrived from CHARGING, AVOIDING or STUCK. That is the Moore style at work.

## FSM in code: a Python example

The cleanest way to code a small FSM is an `enum` for the states and a table for the transitions, with entry and exit actions in one place. The `robot` object stands for whatever drives the motors and reads the sensors.

```python
from enum import Enum, auto


class S(Enum):
    CHARGING = auto()
    CLEANING = auto()
    AVOIDING = auto()
    RETURNING = auto()
    STUCK = auto()


# (current state, event) -> next state. A pair that is not listed is ignored.
TRANSITIONS = {
    (S.CHARGING, "start"): S.CLEANING,
    (S.CLEANING, "bumper_hit"): S.AVOIDING,
    (S.AVOIDING, "turn_done"): S.CLEANING,
    (S.CLEANING, "battery_low"): S.RETURNING,
    (S.AVOIDING, "battery_low"): S.RETURNING,
    (S.RETURNING, "dock_reached"): S.CHARGING,
    (S.CLEANING, "stalled"): S.STUCK,
    (S.AVOIDING, "stalled"): S.STUCK,
    (S.RETURNING, "stalled"): S.STUCK,
    (S.STUCK, "button"): S.CLEANING,
}


class VacuumFSM:
    def __init__(self, robot):
        self.robot = robot
        self.state = S.CHARGING  # initial state

    def guard(self, event):
        if self.state is S.CHARGING and event == "start":
            return self.robot.battery() >= 0.80
        return True

    def handle(self, event):
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None or not self.guard(event):
            return  # this event means nothing in this state
        self.on_exit(self.state)
        self.state = nxt
        self.on_entry(nxt)

    def on_entry(self, state):
        r = self.robot
        if state is S.CLEANING:
            r.brush_on()
            r.drive_forward()
        elif state is S.AVOIDING:
            r.reverse_then_turn()
        elif state is S.RETURNING:
            r.follow_dock_beacon()
        elif state is S.CHARGING:
            r.stop()
            r.start_charging()
        elif state is S.STUCK:
            r.stop()
            r.beep()

    def on_exit(self, state):
        if state is S.CLEANING:
            self.robot.brush_off()

    def tick(self):
        """Run every control cycle. Sensor checks are in priority order,
        because two of them can become true in the same cycle."""
        r = self.robot
        for event, happened in (
            ("stalled", r.wheels_stalled_for(3.0)),
            ("battery_low", r.battery() < 0.15),
            ("bumper_hit", r.bumper_pressed()),
            ("turn_done", r.turn_finished()),
            ("dock_reached", r.on_dock()),
        ):
            if happened and (self.state, event) in TRANSITIONS:
                self.handle(event)
                return
```

User commands such as `start` and `button` arrive by calling `handle()` directly; sensor conditions are turned into events by `tick()`, which the robot's [control loop](/atlas/concept/sense-think-act-loop) calls many times a second. The priority order in `tick()` is not a detail. When conditions are checked regularly in discrete time, two can be true in the same cycle, and a plain FSM does not say which wins, so the code has to ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 2.2).

The same pattern works as a `switch` or `match` statement in C, C++ or Python. Keeping transitions in a table has one advantage: the design is data, so you can print it, test that every state has a way out, or draw the diagram from it.

## Hierarchical state machines and state explosion

A flat FSM grows badly. Each condition that can interrupt *N* states needs *N* arrows. Combine two independent concerns and the states multiply: a mobile manipulator with 5 navigation states and 4 gripper states needs 5 × 4 = 20 combined states in one flat machine. Colledanchise and Ögren list the consequences: adding or removing a state means re-checking a potentially large number of transitions, large machines are hard to modify, and sub-machines are hard to reuse because their transitions depend on internal variables ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 2.1).

The standard fix is **hierarchy**. In 1987 David Harel introduced **statecharts**, which extend ordinary state diagrams with hierarchy, concurrency and communication so that small diagrams can describe complex behaviour ([Harel 1987](https://doi.org/10.1016/0167-6423(87)90035-9)). In a **hierarchical FSM (HFSM)**:

- A **superstate** contains substates, and one of them is marked as the starting substate.
- A transition drawn from a superstate applies to every substate inside it. Wrap CLEANING, AVOIDING and RETURNING in a MOVING superstate and one "wheels stalled" arrow from MOVING to STUCK replaces three.
- Substates **inherit** behaviour from the superstate, so a property set once on MOVING does not have to be repeated in each substate ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 2.2).
- **Orthogonal regions** run independent machines side by side inside one state, so the navigation and gripper machines above can stay separate instead of being multiplied together ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine), [Boost.MSM UML guide](https://www.boost.org/latest/doc/antora/msm/uml-short-guide.html)).

Hierarchy helps a lot but does not remove the problem. The hierarchy is designed by hand, and a task that must be able to jump back and redo any earlier step still needs many arrows inside its superstate ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 2.2).

## FSM vs behaviour tree

A [behaviour tree](/atlas/concept/behavior-trees) is the main alternative for organising robot behaviour, and ROS 2's [Nav2](/atlas/concept/nav2) is built on one. The difference is how control moves. An FSM transition is a **one-way** jump, like a `goto` statement: control leaves one state and lands in another. A behaviour tree uses **two-way** control: a parent node calls a child, and the child reports back success, failure or still running, like a function call ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 1.2).

| | Finite state machine | Behaviour tree |
|---|---|---|
| Control flow | One-way transitions between states | Parent ticks child, child returns a status |
| Adding a behaviour | Re-check existing transitions in and out | Add a subtree; the rest is unchanged |
| Reacting to a new condition | An arrow from every state it can interrupt (or a superstate) | A condition node checked high in the tree |
| Reading a small design | Very clear: boxes and arrows | More machinery for the same result |
| Expressive power | Same: any behaviour tree execution can be described by an FSM, and vice versa | Same |

Behaviour trees came from video games, where character AI had often been written as FSMs, to make behaviour more modular ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 1.1). They are not more powerful, only easier to grow. A reasonable rule of thumb: if the behaviour fits on one page and the states really are separate modes, use an FSM; if you keep adding interrupts and recoveries, consider a tree. The [behaviour trees entry](/atlas/concept/behavior-trees) covers how trees work in detail.

## Where you'll see it

- **Inside ROS 2.** A managed (lifecycle) node has four primary states, `Unconfigured`, `Inactive`, `Active` and `Finalized`, and an external supervisor moves it between them with transitions such as `configure` and `shutdown` ([ROS 2 design: managed nodes](https://design.ros2.org/articles/node_lifecycle.html)). Nav2's servers all use this lifecycle for a predictable start-up and shut-down ([Macenski et al. 2020](https://arxiv.org/abs/2003.00368)).
- **SMACH.** A task-level library from ROS 1 for composing robot behaviour. At its core it is a ROS-independent Python library for building hierarchical state machines ([SMACH package description](https://github.com/ros/executive_smach/blob/noetic-devel/smach/package.xml)).
- **FlexBE.** A behaviour engine for ROS 2 in which behaviours are hierarchical state machines: states are active actions and transitions are the reaction to their outcomes. An operator can restrict transitions or trigger them by hand, and a graphical editor builds the machines ([FlexBE](https://github.com/FlexBE/flexbe_behavior_engine)).
- **YASMIN.** A state machine library for ROS 2, Python and C++, with ready-made states that call ROS 2 actions, services and topics, a shared "blackboard" for data, concurrent and orthogonal states, nesting (its Nav2 demo is a hierarchical FSM) and a web viewer ([YASMIN](https://github.com/uleroboticsgroup/yasmin)).
- **Nav2, which chose not to.** Nav2's authors wrote that as states and transitions grow, modelling complex multi-step tasks as FSMs "can become intractably complex", so its navigator is a behaviour tree loaded from an XML file at run time ([Macenski et al. 2020](https://arxiv.org/abs/2003.00368), [nav2_bt_navigator](https://github.com/ros-navigation/navigation2/tree/main/nav2_bt_navigator)).
- **Factory automation.** An FSM can be built in hardware from logic gates and flip-flops, relays or a programmable logic controller (PLC) ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)). PLC programmers also have a graphical language of their own, the sequential function chart, which is based on GRAFCET and is one of the five languages in the IEC 61131-3 standard ([Wikipedia: sequential function chart](https://en.wikipedia.org/wiki/Sequential_function_chart)).

## Limits

- **State explosion.** Interrupts and independent concerns multiply arrows and states. Hierarchy slows this down; it does not stop it.
- **Poor reuse.** A sub-machine's transitions often depend on the machine around it, so lifting it into another project takes rework ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084)).
- **Memory is only the state.** An FSM cannot count or remember without limit; its memory is bounded by its number of states ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine)). Real robot code keeps counters, maps and goals in ordinary variables alongside the machine, which is why libraries such as YASMIN add a shared blackboard.
- **It decides what to do, not how.** Steering, balancing and holding a speed belong to continuous controllers such as a [PID controller](/atlas/concept/pid-controller) running inside a state.

## Going deeper

- **Formal roots.** In theory a deterministic FSM is a 5-tuple: input alphabet, set of states, initial state, transition function and set of final (accepting) states. The output models are named after Edward Moore (1956) and George Mealy (1955); Hopcroft's algorithm finds the smallest machine that behaves the same ([Wikipedia](https://en.wikipedia.org/wiki/Finite-state_machine), [Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), references).
- **Outcome-based machines.** ROS libraries such as FlexBE and YASMIN turn the textbook model around slightly: each state runs some work and returns an outcome (YASMIN's ROS states use basic outcomes such as `SUCCEED`, `ABORT`, `CANCEL` and `TIMEOUT`), and the transitions map each outcome to the next state ([FlexBE](https://github.com/FlexBE/flexbe_behavior_engine), [YASMIN](https://github.com/uleroboticsgroup/yasmin)). The "event" is the result of the state's own work.
- **Trees and machines are equivalent.** Every execution a behaviour tree describes can be described by an FSM and the other way round, so choosing between them is about which is easier to build, read and change, not about what is possible ([Colledanchise & Ögren](https://arxiv.org/abs/1709.00084), ch. 2.2).

## Why it matters

Many robots spend their lives switching between a handful of modes, and a lot of strange robot behaviour is a mode problem: the robot did not know it was supposed to stop, or two rules fired at once. Drawing the robot as states and arrows forces every one of those decisions into the open, before the robot finds them. The FSM is also the baseline that every alternative, from statecharts to behaviour trees, is explained against, and anyone who uses ROS 2 managed (lifecycle) nodes, as Nav2 does, is already working with one.

## Common questions

### What is an FSM in robotics?

A finite state machine is a way of organising a robot's behaviour as a fixed list of modes, such as charging, cleaning and returning to the dock, where the robot is in exactly one mode at a time and switches only when a named event happens, such as a bumper hit or a low battery. Libraries such as SMACH, FlexBE and YASMIN implement it for ROS.

### What is the difference between a state machine and a behaviour tree?

In a state machine, control jumps one way from state to state along arrows, so every new interruption needs arrows from each state it can interrupt. In a behaviour tree, a parent asks its children to run and they report back success, failure or running, so new behaviour is added as a new branch. Both can express the same behaviours; trees are easier to extend, FSMs are clearer for a few modes.

### What is the difference between a Moore and a Mealy machine?

In a Moore machine the output depends only on the current state, so the work is done when a state is entered. In a Mealy machine the output depends on the state and the input, so the work is done on the transition, which often needs fewer states. Most robot code mixes both.
