# ROS2 Actions

A ROS 2 action is how one piece of a robot's software asks another to carry out a job that takes a while — drive across a room, rotate to face a direction, lift an arm — while watching it happen and keeping the option to stop it. The ROS 2 documentation calls an action "a long-running remote procedure call with feedback and the ability to cancel or preempt the goal."

The useful picture is a courier booking: you place the order (the **goal**), you get tracking updates on the way (**feedback**), you get a delivery confirmation (the **result**), and you can cancel mid-journey.

## The three parts

Actions are intended for long-running tasks and consist of three parts: a goal, feedback, and a result. That feedback stream is what a plain request/reply call cannot give you — a [service](/atlas/concept/ros2-services) returns one answer and nothing in between.

## When do you reach for an action?

[ROS 2](/atlas/concept/ros2) has three ways for [nodes](/atlas/concept/ros2-nodes) to talk. Choosing the wrong one is the most common beginner mistake in the whole framework.

| Pattern | Shape of the conversation | Reach for it when | Can you cancel? |
|---|---|---|---|
| [Topic](/atlas/concept/ros2-topics) | Fire-and-forget broadcast, one-way, any number of listeners | A continuous stream of data: camera frames, wheel speeds, battery level | Nothing to cancel — there is no job |
| [Service](/atlas/concept/ros2-services) | One request, one response, returns quickly | A short question or command that needs an answer: "save the map", "what are your parameters?" | No |
| Action | Goal, then a stream of feedback, then a result | A job that takes seconds or minutes and whose progress matters: navigate, grasp, scan, dock | Yes — by the client, or aborted by the server |

Actions carry real setup and monitoring overhead, so the ROS 2 docs are blunt about the other direction too: if you need a short request, use a service instead.

## Client and server

Actions use a client-server model. An action client node sends a goal to an action server node, which acknowledges the goal and returns a stream of feedback and a result. Any number of clients may send goals to the same action name, but there should only ever be one action server per action name — if two servers claim the same name, which one receives a request is undefined.

The server is in charge. It can accept a goal, reject it, or **abort** one it has already started. In the turtlesim tutorial, sending a second rotation goal before the first finishes makes the server abort the first one. A different server might have queued the goals or refused the new one instead — never assume.

## What an action looks like

An action's type is defined in a `.action` file with two `---` separators. Here is turtlesim's `RotateAbsolute`, exactly as `ros2 interface show` prints it:

```text
# The desired heading in radians
float32 theta
---
# The angular displacement in radians to the starting position
float32 delta
---
# The remaining rotation in radians
float32 remaining
```

The part above the first `---` is the goal, the next is the result, and the last is the feedback. You can drive one from a terminal without writing any code:

```console
$ ros2 action send_goal /turtle1/rotate_absolute \
    turtlesim/action/RotateAbsolute "{theta: 1.57}" --feedback
```

Every goal gets a unique ID, which the design uses to mitigate goal-ID collisions between clients, and the terminal prints `remaining` repeatedly until the goal finishes with `SUCCEEDED`.

## A real robot example

[Nav2](/atlas/concept/nav2), the standard ROS 2 navigation stack, exposes navigation as an action. Its `NavigateToPose` goal is a target pose; its feedback includes `distance_remaining`, `estimated_time_remaining` and `number_of_recoveries`; its result shape has changed between distributions, so check the version you are on. That is the whole argument for actions in one interface: you ask once, you watch, and you can change your mind.

## Common questions

### Is an action just a slow service?

No. A service returns a single response and cannot be cancelled. An action adds steady feedback while the work happens and a cancel path, which is why ROS 2 reserves it for long-running procedures.

### What happens if I cancel halfway?

The client requests cancellation; the server decides whether to accept it. If it does, the goal moves to a `CANCELING` state and then finishes as `CANCELED` rather than `SUCCEEDED`. A goal the server stops on its own is `ABORTED` instead.

### Can I see an action's internal topics?

Not by default. ROS 2 deliberately hides the services and topics that make up an action from `ros2 topic list` and `ros2 service list`; you have to pass the option for hidden entries to see them.
