colcon is the command-line tool that builds a ROS 2 workspace. You point it at a folder of packages, it works out which package depends on which, builds them in that order, and installs the results with a setup script that makes them usable from your terminal.

On the left, the src folder holds three packages: my_msgs, my_driver and my_app, with arrows showing my_driver depends on my_msgs and my_app depends on both. In the middle, colcon build reads those dependencies and builds them in order: 1 my_msgs, 2 my_driver, 3 my_app. On the right, three new folders appear next to src: build for intermediate files, install for the finished packages and their setup scripts, and log for build logs. Below, the loop every ROS 2 developer repeats: colcon build, then source install/setup.bash, then ros2 run or ros2 launch](/images/atlas/diagrams/colcon.svg)

## Start here: what problem does colcon solve?

A robot's software in [ROS 2](/atlas/concept/ros2) is split into **packages**. One package might hold only message definitions, another a motor driver, another the navigation logic, another the launch files that start everything. A real robot can have dozens of them, many written by other people, some in C++ and some in Python.

Those packages depend on each other. The driver cannot compile until the message definitions it uses exist. The application cannot run until the driver is installed. Building them by hand means remembering that order and running a different build command for each kind of package.

colcon does that bookkeeping for you. Its own documentation describes it as a tool "to improve the workflow of building, testing and using multiple software packages", which "automates the process, handles the ordering and sets up the environment to use the packages." The name is short for **collective construction**.

## The three-command loop

Almost all day-to-day ROS 2 work is this loop, run from the root of your workspace (the folder that contains `src/`):

```bash
# Terminal 1: build only
cd ~/ros2_ws
colcon build --symlink-install    # 1. build every package in src/

# Terminal 2: source and run
cd ~/ros2_ws
source install/setup.bash         # 2. load the result into this terminal
ros2 run my_app my_node           # 3. use it (or ros2 launch ...)
```

1. **Build.** `colcon build` finds the packages, orders them and builds each one.
2. **Source.** colcon writes setup scripts into `install/`. Sourcing one adds your packages to the paths the `ros2` command searches. Until you do this in a terminal, that terminal cannot see what you built.
3. **Run.** `ros2 run` starts a single [node](/atlas/concept/ros-node); `ros2 launch` starts a whole system from a [launch file](/atlas/concept/ros2-launch).

Change code, build again in terminal 1, run again in terminal 2. Keep the build terminal free of your workspace's setup script (see the sourcing section below). Source again in each new terminal, and after a build adds a new package.

## How it works

### 1. The workspace

A colcon workspace is simply a folder. By convention your packages go in a `src/` subfolder; colcon searches the subfolders for packages, so `src/` is a habit rather than a rule. Before the first build the workspace is just:

```text
ros2_ws/
└── src/
    ├── my_msgs/
    ├── my_driver/
    └── my_app/
```

### 2. Discovery and the dependency graph

colcon looks for packages in the workspace and reads each package's manifest. For ROS packages that is `package.xml`, in the format defined by REP 149 (the older format 2 is also accepted). The manifest lists what the package depends on, and from those lists colcon builds a **dependency graph** and sorts it so every package comes after the packages it needs. You can see the result yourself:

```bash
colcon list     # every package colcon found
colcon graph    # the same packages in build order, with their dependencies
```

### 3. Building each package with its own tool

colcon does not compile anything itself. For each package it calls that package's own build system, chosen by its **build type**. The ROS 2 documentation recommends `ament_cmake` (C++ packages built through CMake) and `ament_python` (Python packages built through setuptools), and plain `cmake` packages are supported too. That is why one workspace can mix C++ and Python packages and still build with one command.

Packages that do not depend on each other can build at the same time. colcon's parallel executor, the default when it is installed, builds up to one package per logical CPU core at a time, and each CMake package also compiles with one make job per core.

### 4. Out-of-source builds and the three new folders

colcon directs every package to build out of source, so build files go into separate folders, not into your source code. After the first build, three folders appear next to `src/`:

| Folder | What is in it | Safe to delete? |
|---|---|---|
| `build/` | Intermediate files, one subfolder per package (where CMake actually runs) | Yes, but the next build starts from scratch. If you built with `--symlink-install`, delete `install/` too, because it links into `build/` |
| `install/` | The finished packages, plus the `setup.bash` / `local_setup.bash` scripts you source | Yes, then rebuild. Anything sourcing it breaks until you do |
| `log/` | Logs of every colcon run, the first place to look when a build fails | Yes |

By default each package is installed into its own subfolder of `install/` (an **isolated** install). That gives better isolation between packages, so a dependency you forgot to declare is more likely to show up as a build error. ROS 1 users will notice there is no `devel/` space; colcon requires every package to install itself.

### 5. Sourcing: underlays and overlays

The workspace you build sits on top of something else, usually your ROS 2 installation in `/opt/ros/<distro>`. The ROS 2 documentation calls the installation the **underlay** and your workspace the **overlay**. The overlay can add packages and can also override a package from the underlay with your own copy (this works for most packages, but the colcon docs list cases where an override does not fully take effect).

Two setup scripts are generated, and the difference matters:

- `install/setup.bash` loads your workspace **and** the underlays it was built against.
- `install/local_setup.bash` loads **only** your workspace, for when the underlay is already sourced.

The ROS 2 workspace tutorial adds an important rule: source the overlay in a **new terminal**, not the one you built in, because "sourcing an overlay in the same terminal where you built, or likewise building where an overlay is sourced, may create complex issues."

## Worked example: building only what you need

Take the three packages from the diagram: `my_msgs` (message definitions), `my_driver` (depends on `my_msgs`) and `my_app` (depends on both). A full `colcon build` builds them in the order my_msgs → my_driver → my_app. On a large workspace, rebuilding everything after every change wastes minutes, so colcon has **package selection** flags. What each one builds here:

| You run | What gets built | When to use it |
|---|---|---|
| `colcon build` | my_msgs, my_driver, my_app | First build, or after pulling many changes |
| `colcon build --packages-select my_app` | my_app only | You changed only my_app and its dependencies are already built |
| `colcon build --packages-up-to my_app` | my_msgs, my_driver, my_app | First build of my_app in a big workspace: it plus everything it needs, nothing else |
| `colcon build --packages-above my_msgs` | my_msgs, my_driver, my_app | You changed a message in my_msgs: rebuild it and everything that depends on it |
| `colcon build --packages-skip my_app` | my_msgs, my_driver | my_app is broken and you want the rest |

The catch with `--packages-select` is in the colcon docs: it "assumes that you have built dependencies of the selected packages within the workspace before." On a fresh clone it usually fails (unless the underlay already provides those dependencies), where `--packages-up-to` succeeds. In this tiny workspace three of the commands build the same packages; in a workspace of fifty they would not.

## Flags worth knowing

| Flag | What it does | Why you would use it |
|---|---|---|
| `--symlink-install` | Links installed files back to the source and build folders instead of copying them, where possible | Edit an existing Python file, launch file or YAML config and the change takes effect without rebuilding (new files still need a build) |
| `--packages-select`, `--packages-up-to`, `--packages-above` | Build a subset (see the table above) | Faster iteration |
| `--executor sequential` | Build one package at a time | The ROS 2 docs suggest it on CPU-, RAM- or I/O-limited machines such as a Raspberry Pi, where a parallel build can freeze the screen and mouse |
| `--parallel-workers N` | Cap the number of packages built at once | A middle ground between full parallel and sequential. It limits packages, not compiler jobs inside a package; set `MAKEFLAGS=-jN` for that |
| `--event-handlers console_direct+` | Print build output live instead of only to `log/` | Watching a slow or failing build |
| `--continue-on-error` | Keep building other packages when one fails (packages that depend on it are skipped) | Find every broken package in one run |
| `--cmake-args -DCMAKE_BUILD_TYPE=Release` | Pass options through to CMake | Optimised C++ builds; `-DBUILD_TESTING=OFF` skips building tests |
| `--merge-install` | Install all packages into one shared prefix instead of one folder each | Shorter environment variables; the ROS 2 docs use it on Windows, which limits path length. The cost is weaker isolation between packages |

Note that `--symlink-install` only helps for existing files that need no compiling. C++ changes, new files, interface (`.msg`/`.srv`/`.action`) changes, and changes to `CMakeLists.txt`, `package.xml` or `setup.py` still need a build.

To leave a folder out of the build entirely, put an empty file named `COLCON_IGNORE` in it.

## Testing with colcon

The same tool runs tests across the workspace:

```bash
colcon test                           # run every package's tests
colcon test --packages-select my_app  # just one package
colcon test-result --verbose          # show details of each failure
```

By default `colcon test` exits successfully even when tests fail. In CI, use `colcon test --return-code-on-test-failure`, or follow it with `colcon test-result --verbose`, which exits non-zero on any failure.

colcon passes test runs to each package's own test tool, pytest for Python and CTest for CMake, and arguments can go straight through: `colcon test --packages-select my_app --ctest-args -R my_test` runs only the CMake tests whose names match `my_test`.

## Common errors and what they mean

| Symptom | Usual cause | Fix |
|---|---|---|
| `colcon: command not found` | colcon is not installed (it is a separate package from ROS 2) | `sudo apt install python3-colcon-common-extensions` (Ubuntu) or `pip install -U colcon-common-extensions` |
| `Package 'my_pkg' not found` after a successful build | This terminal has not sourced the workspace | `source install/setup.bash` from the workspace root (full walkthrough: [ros2: command not found](/ros2/fix/ros2-command-not-found)) |
| `build/`, `install/` and `log/` appeared inside `src/` | colcon was run from the wrong folder | Delete those three folders from `src/` and run colcon from the workspace root |
| CMake says it could not find a package configuration file for a dependency | The underlay is not sourced, a system dependency is missing, or a dependency in this workspace has not been built yet (for example after `--packages-select`) | Source `/opt/ros/<distro>/setup.bash`, then run `rosdep install -i --from-path src --rosdistro <distro> -y` |
| A build passes on your machine but fails in a fresh terminal, in CI or for a colleague | You built in a terminal where this workspace's `install/` was already sourced, which hid a dependency missing from `package.xml` | Build in one terminal; source and run in another |
| The machine freezes during the build | Too many compiler jobs for the RAM: colcon builds several packages at once, and each C++ package also compiles on every core | `MAKEFLAGS=-j2 colcon build --executor sequential` (lower `-j` further if needed) |
| A Python edit has no effect | Built without `--symlink-install`, so the old copy in `install/` runs | Rebuild. To switch to `--symlink-install`, delete `build/` and `install/` first (switching an existing workspace without cleaning can fail) |

## colcon vs catkin_make

ROS 1 developers built with `catkin_make` (or `catkin build` from catkin_tools). The ROS 2 documentation describes colcon as "an iteration on" `catkin_make`, `catkin_make_isolated`, `catkin_tools` and `ament_tools`. The practical differences:

| | catkin_make (ROS 1) | colcon (ROS 2) |
|---|---|---|
| Build style | One combined CMake project | Each package built separately, in dependency order |
| devel space | Yes, a `devel/` folder you can source without installing | No; every package must install. `--symlink-install` gives the fast-edit benefit instead |
| Package types | catkin (CMake) | ament_cmake, ament_python, plain CMake; ROS 1 catkin packages too |
| Script you source | `devel/setup.bash` | `install/setup.bash` |

colcon is not tied to ROS. It builds plain CMake and Python packages, and a ROS 2 installation built from source is itself a colcon workspace.

## Where you'll see it

- **Every ROS 2 tutorial and project**: the build step in the ROS 2 beginner tutorials, and in the build instructions of most ROS 2 packages on GitHub.
- **Building ROS 2 from source**: a source installation of ROS 2 is a colcon workspace, which you then use as the underlay for your own.
- **[Docker](/atlas/concept/docker-robotics) images and CI**: a Dockerfile for a ROS 2 robot typically runs `colcon build` as one of its steps, and CI pipelines for ROS 2 code typically run `colcon build` and `colcon test` on every change.
- **Mixed-language robots**: C++ drivers and Python nodes in one workspace, one build command.

## Why it matters

colcon is the step between writing robot code and running it, so it is often the first thing that goes wrong for a ROS 2 beginner: the build works but `ros2 run` says the package is not found, or a change does not show up. Almost every one of those problems comes back to three ideas on this page: the workspace has `src`, `build`, `install` and `log` folders; the terminal only sees what you have sourced; and packages build in dependency order. Get those right and colcon becomes the boring, reliable command it is meant to be.

## Common questions

### What is colcon in ROS 2?

colcon is the build tool used in ROS 2. It finds the packages in a workspace, works out their dependency order from each package's `package.xml`, builds them with their own build systems (CMake for C++, setuptools for Python) and installs them with setup scripts you source to use them. The name stands for "collective construction".

### What does colcon build do?

It builds every package in the current workspace in dependency order, putting intermediate files in `build/`, the finished packages and their setup scripts in `install/`, and logs in `log/`. Run it from the workspace root, then `source install/setup.bash` before using the packages.

### Why does ros2 run say my package is not found after colcon build?

Because the terminal has not loaded the workspace. Building writes your package into `install/`, but a terminal only searches it after `source install/setup.bash` has been run in that terminal. Every new terminal needs it again, unless you add it to your shell's startup file.

### Do I need to run colcon build after every change?

For C++ code, and for changes to `package.xml`, `CMakeLists.txt` or `setup.py`, yes. For edits to existing Python, launch and config files, not if you built with `--symlink-install`: the installed copy is a link back to your source, so the edit takes effect the next time you run the node. Adding a new file still needs a build.
